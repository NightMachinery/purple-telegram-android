# Direct-share shortcuts and Work Mode

Purple publishes a single cross-account snapshot instead of letting each account replace the app-wide shortcut set. The selected account leads each hint-rank round, followed by the other signed-in accounts in slot order. Hints retain their order within an account. The compose shortcut, existing conversation shortcuts and unrelated dynamic targets consume the OS budget before frequent-chat hints. Publication never exceeds the available OS count, capped at64 owned targets.

Frequent-chat IDs include the account key, so the same peer in two accounts has separate targets. Their intents carry the current slot. Notification conversation IDs also include the account key and their intents carry the slot and dialog. A slot reused by another account does not inherit the previous account's target identity.

Work Mode's hidden-everywhere and hidden-from-suggestions predicates apply to every account snapshot. A passcode suppresses chat targets. Hidden direct targets are removed incrementally, including cached long-lived entries. Existing ranks, labels, avatars, routing or direct-share eligibility are updated only when they change. Unrelated shortcut types are preserved; no remove-all operation is used.

A bounded in-memory cache retains up to64 removed conversation descriptors. Unhide can restore an existing descriptor while its original account and lifetime remain current. The cache contains OS shortcut metadata, not chat history, and does not survive process restart. After restart a new notification can recreate a conversation target. Legacy unqualified ndid_ descriptors are retired. A current slot or a unique loaded dialog cache does not prove their historical owner. New notifications use qualified IDs. No contact ratings, raw hints or recent-search records are rewritten.

A single pending UI snapshot and serial publication coalesce requests. The owned publisher checks its request generation, Work Mode generation, selected account and all captured account lifetimes before publication. It checks authority again at each OS mutation, after preparing icons. A superseded plan publishes nothing; newer work is collected after the current task finishes. OS refusal is logged and retried only by a later rebuild request. This is an input/rank policy for Android; the OS may independently rank the share sheet.

The MediaDataController.buildShortcuts hook delegates to PurpleDirectShare. The two NotificationsController hooks qualify conversation IDs and hand their publication to the same owner. PurpleGate reload calls the owner once. Host tests exercise the actual AGP-compiled publication model through a synthetic ShortcutManager port; no device or OEM ranking behavior is claimed.

The share-target relay is required because LaunchActivity resolves a shortcut ID to a dialog and token without adopting the shortcut intent's account. The relay validates current dynamic/cached membership, account identity, token and Work Mode visibility, then forwards a copy of the share intent with verified routing. Unsupported actions are refused; an unavailable target falls back to the ordinary picker with routing extras removed. Intent copying preserves content and URI grants. No protected archive source is changed. Conversation uninstall removes the qualified ID and its retained descriptor.

Every new shortcut intent, including explicit launcher pins, conversation shortcuts, compose and relay handoffs, carries its stable account key, per-login nonce and peer. The nonce is the existing atomic UserConfig login anchor; no new session identifier is generated during shortcut publication. If that anchor is missing or malformed, publication refuses for that account. Same-login restarts retain routing; logout, slot reuse and a new login revoke old intents. OpenChatReceiver and the attached-bot receiver forward identity unchanged and mark shortcut provenance without reading or validating the account inventory. LaunchActivity initializes the inventory normally, then checks before selecting an account and again before common dispatch, with a short refusal toast. Pinned shortcuts can survive OS removal, so final admission is the authority. Pin-only descriptors are not repeatedly removed from the dynamic set.

The common receiver initializes the verified recipient for both SEND and SEND_MULTIPLE. Generic shares retain the ordinary picker; stale marked routes are refused. Work Mode visibility is checked again at final admission. Host regressions preserve a launcher pin after dynamic/long-lived removal, test a reused slot and a same-user new login, and adapt all six RoutingProbe scenarios from review.

Cold-start admission happens only in initialized LaunchActivity. Forwarders cannot distinguish an unloaded inventory from logout, so they do not attempt account admission. Their provenance mark also prevents an old unbound shortcut from becoming an ordinary unmarked notification intent. Actual AGP receiver regressions cover chat/bot pins with an initially empty inventory, valid admission after initialization, slot reuse, same-user new login and unbound legacy pins.
