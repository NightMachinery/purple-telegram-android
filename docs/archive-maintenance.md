# Confirmed local archive maintenance

Archive settings offers Empty trash and Clear edit history for the opening account. The dedicated Deleted messages view offers the same actions for its captured typed parent chat and trusted migration aliases. Confirmation names that account and scope, reports observed message/version counts, and explains that all topics, collections and representations in that parent are included. Topic and display filters never narrow a purge. No action changes Telegram messages, starts a download or removes a completed user export.

Empty trash removes every retained version of Deleted, Expired and Consumed messages in that scope. Clear edit history keeps each exact latest captured body, including a deleted message's latest body. Shared blobs, leases and incomplete jobs can retain bytes, so the confirmation does not promise freed space. A changed archive revision requires another review before Begin can commit.

## Authority and the committed boundary

The model captures the original account, identity lifetime, login, store incarnation, selection generation, resolved policy and parent/alias scope. Parent metadata is watched on the UI thread; archive tasks consume only its revocation flag. Lock, selection or scope changes withdraw confirmation and queued results. Cancellation before Begin changes nothing. Closing the dialog or switching selection after Begin stops observation but cannot cancel or retarget the committed operation.

Core's Make/Confirm/Begin planners supply the revision, generation and feasibility checks. Store.executeMaintenance passes through the same checked SQL executor as every ordinary write. Before returning from a committed Begin, or an uncertain completion whose durable gate is present, it withdraws Deleted/history views, media capabilities and queued deliveries. An ordinary reader or write cannot pass the maintenance gate.

Ingress tickets bind queued capture, acquired-source and lifecycle work to the opening worker, store and memory epoch before dispatch. Begin advances that epoch; startup pending maintenance advances it before recovery. Old work cannot obtain a fresh generation to resurrect removed data. Genuinely new observations after Finish get fresh admission. Refused capture remains an explicit gap.

## Recovery and bounded work

Startup admits the encrypted header and authenticated sealed operation before ordinary capture or query access. The SQL operation id, kind, scope, phase, cursor, revision and generation must match the sealed journal. Missing, malformed, unknown or mismatched evidence remains refused. Retry resumes that exact journal; it does not create a replacement operation. Explicit account archive discard remains available when admission refuses.

One runner owns each store on its account queue. A continuation reads at most 128 rows and supplies authenticated original row/head and all owned-copy proof columns. Evidence is capped at 12 MiB per worker step; an oversized single row refuses explicitly. Core supplies the processed prefix and cursor. The next step rereads any suffix, and an empty page must pass core's exhaustion proof before a phase advances. Every committed page yields to queued account control work.

Finish renews schema and capture admission before Ready. Renewal has three bounded attempts; exhaustion is visible as held maintenance. A new explicit Retry can attempt the retained operation again. Failures retain a reason and ownership, never successful zero counts. If a cleanup handle cannot close, Retry first queues one coalesced attempt to close that retained runner. A fresh runner can begin only after close acknowledgement. A persistent or uncertain close remains held; no descriptor is guessed closed and no cleanup is acknowledged speculatively. Login replacement, discard and logout keep their existing authority fences. Logout revokes immediately and erases the account archive asynchronously, including a pending purge, without touching another account.

Restart recovery is restricted to sources already orphaned when this process began. Each newly created staging binding carries a random process token inside its existing authenticated encrypted envelope; core's job and source binding are unchanged. A missing token identifies a legacy retained source, and a malformed token refuses. Recovery skips a current-process binding, even if a later cleanup scan encounters it. For a prior-process source, recovery also checks the bounded acquired-source registry for a live owner of that exact store and staging job, including a producer that adopted an old job. It repeats the ownership check before each finalizer step and releases its own finalizer if a producer takes ownership. This avoids an unbounded process-wide set of source ids. Intentional retirement is separately proved by the purge generations below; it never authorizes recovery to change a live post-purge source.

Intentional retirement is not a retention gap. A reader release defers while the maintenance gate is active and retains its durable pin until release can commit. Orphan release is likewise deferred. Ordinary staging recovery starts only after the maintenance runner has swept acknowledged cancelled jobs and finished owned garbage cleanup. It authenticates each retained binding, compares its exact account/store/work fence and its original account/chat purge generations with an authenticated current snapshot, and treats deliberately retired sources as expected cancellation. Physical cancelled-job cleanup remains owned by the authenticated maintenance runner, before ordinary recovery starts. Retired completed-job bindings remain available as authenticated evidence; this fix does not add an unjournaled deletion path. A stale head alone is not proof of intentional removal. Unreadable bindings, unchanged-generation corruption and genuine acquisition failures still record gaps. An active acquired source is exempted from failure reporting only after crossing a committed memory epoch and proving the matching durable purge generation; a failure observed before that boundary still reports normally.

Garbage cleanup first durably commits the core's GarbagePending intent. It rereads exact blob identity and fresh reference/lease absence before physical removal, then commits GarbageComplete only after checked absence. Shared or leased blobs remain. Directory cleanup yields after at most 64 operations and refuses unsafe paths or depth above 16. Cancelled staging cleanup and canonical blob cleanup stay inside the original owned store. Restart resumes both logical purge and interrupted physical cleanup; no Telegram cache or user export is a cleanup target.

## Headless checks

The archive host runner uses actual AGP production classes, checked core JNI and the bundled SQLite shim. Maintenance fixtures cover both operations and account/chat scope, topic and representation breadth, stale confirmation, the committed revocation boundary, late ingress, processed prefixes and exhaustion refusal, shared media GC, split bodies, uncertain commit acknowledgement, logout/discard isolation, selection changes, sealed-journal refusal and process-death cuts across purge and GC phases. Host crypto ports do not qualify hardware Keystore or Android UI behavior.
