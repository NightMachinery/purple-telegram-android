# Lost sync-chat recovery

A missing Purple mark and a confirmed inaccessible chat are different outcomes.
Searching keeps the existing 30, 120 and 600 second retry schedule. A timeout,
transport error, partial search or unknown direct read never establishes ChatGone.
Reconnect or explicit Retry resolves the captured account and chat again.

Recovery has three choices: Create a new sync chat, Choose another sync chat, or
Mark this chat again. Production recovery remains constant OFF. The Sync screen
shows a non-actionable qualification hold and constructs no actionable recovery
rows while OFF. Click, confirmation and
public entry guards also refuse. Synthetic host injection is the only qualified
route; no device or Telegram request is part of this slice.

## Move to another chat

Create provisions only a channel, then hands it to the existing Change/Carry
controller. Choose uses that controller directly. Both resolve afresh before any
provisioning and recheck the accepted source, winner, binding, state and admitted
cache before starting Carry. A newer winner, different login or changed opening
holds. Repeated Create on one controller cannot start another channel. An
uncertain creation stays in the existing provision journal for reconciliation.
There is no fresh-setup bypass for a bound account.

When O is protected or definitely gone, Carry uses this install's exact verified
local base. A missing or mismatched base is a visible MissingLocalVersion hold, with a
message explaining that unsynced edits will not replace the saved version.
Unsynced desired/editor text never substitutes for that version. Other devices'
settings can only be recovered from the records actually available; this install
cannot invent missing versions or reconstruct unavailable history.

A protected O is never called gone and receives no pending send. The existing
ReconcileProtectedStageForCarry contract reconciles issued intent against a new
complete O inventory. Exact found own content is carried; definite absence permits
restaging in N; uncertainty holds. A confirmed lost O uses AbandonStageForLostChat.
The durable Issued floor and Pending chronology fences remain unchanged. Pending
content is retained and restaged through the core rather than silently discarded.

## Mark this chat again

This is core RepairMark with O=N. It posts only a replacement mark and updates
its admitted mark cache. The settings state, binding and version ledger remain
byte-identical. No settings plan, new settings identity or empty stream is made.
It does not need to invent a settings base just to restore a mark.

Repair requires the exact captured positive mark's R3 MarkGone, a complete fresh
resolution with no newer winner, a readable chat, current eligibility, known
readers and original reader consent. ChatGone, an unreadable chat, an unproven
missing mark, a pending stage, unknown readers/roster or lost rights holds.
C6 compares with the original reader snapshot: known additions warn and continue,
unknown population or lost rights hold. The original baseline and sticky warning
survive the repair. Final per-attempt Carry admission remains in force before an
actual mark write; a late winner or revoked login cannot grant permission.

## Qualification

The canonical recovery host suite uses actual AGP business classes, real JNI and
local files with synthetic resolution, scheduling and transport. It pins repair
state preservation, reader changes, OFF controls, account/login/winner fencing,
retry/reconnect, Create idempotence, protected pending stages and exact-base holds.
Inherited suites cover discovery retry/error semantics, store durability, per-send
admission, rate limits and Pending chronology. Host qualification does not prove
real Telegram server behavior, Android lifecycle or physical power-loss behavior.
