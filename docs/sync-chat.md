# Magic Purple Sync

Purple maps Android TL objects to the shared sync-chat contract. `PurpleSyncChatCore` exposes typed ownership and eligibility through `sync_chat_bridge.cpp`. `PurpleSyncChatFacts` consumes current native messages, peers and matching full info. Missing, contradictory or unsupported facts remain Unknown.

`PurpleSyncMagicCore` carries the Magic Purple Sync policy of purple-core (`purple_sync_chat_magic.h`) through `sync_magic_bridge.cpp`: the title and eligibility check, the lookup plan, the Verify step and every edit of the per-device binding (sync/chat.json), whose waits, problem and migration step it stores. Each operation refuses a null binding, so a failed edit is never read as "no binding". The binding is the account's, not the sync state's: the account sync store and every scan of its folder (interrupted-write recovery, Start again, set aside) accept sync/chat.json and the `owner-<n>.tmp` its writer can leave after a crash, by exact name, and Start again and a set aside leave the binding in place.

Path guard: the durable file layer (`PurpleAccountFileSnapshot.durable*`, the native `sync_files_bridge.cpp`) walks from the app's files directory, never from "/", which Android refuses an app to read; any sync path that is not strictly below that directory (or has an empty, "." or ".." part) is refused before anything is opened, with status `PathOutsideRoot` and the diagnostic line `sync_chat path_refused reason=path_outside_root`, and parent walks stop at the root. The modern host suite refuses every open of "/" (`tests/modern_sync/rootdeny.c`) so a walk from "/" fails there as on the device. Link checks look only at the last component of a path (`PurpleAccountFileSnapshot.notLink`): Android reaches the files directory through the link /data/user/0, and comparing whole canonical paths refused every retained base there, so a magic publish posted its record and then failed its local commit with InvalidRetention. A device whose commit already failed keeps the post staged; its store now opens as it is, the Check shows the post as unfinished, and Finish sending confirms the record found in the chat without sending it again (the core's ConfirmFound plan).

`PurpleSyncMagicChat` runs the lookup for one account, and `PurpleSyncMagicTelegram` connects it to MessagesController and ConnectionsManager. Startup, the Sync screen, a manual run, automatic sync and a post all call the same lookup, one at a time; a call arriving while one runs shares its result. The lookup uses a bound chat that is in memory without a request and verifies it with `channels.getFullChannel` at most once a day before a post. After a cold start the archived magic chat is usually not in memory yet, so the lookup reads it from the local database (`MessagesStorage.getChat` on the storage queue) before anything else. Without a binding it takes a magic chat from the local lists.

The absence proof is the lists themselves (core `listsComplete`): the main list and the archive folder are both loaded to the server's end (`isServerDialogsEndReached(0)` and `(1)`). The lookup reads the account's real dialogs (`dialogs_dict`), never the per-folder arrays or the views that Work Mode, folders and the hidden sync chat filter, so no view can hide a magic chat from the proof. Until the lists are complete, an unbound lookup without a magic chat, or one whose bound chat is in neither memory nor the database, asks upstream's own loader for the next page (`MessagesController.loadDialogs(folder, -1, 100, fromCache)`, as scrolling the chat list does: the cache first, then the server), one page at a time, and plans again when `dialogsNeedReload` reports that the page landed. It sends no request of its own for this. There is no server-side search, and `messages.getAllChats` is not in the client's pinned layer (the server answers `400 INPUT_METHOD_INVALID`). After 60 seconds of paging in one lookup it answers a wait of Purple's own and looks again a minute later (`lists_loading`); it never creates from incomplete lists. An unbound lookup that sees only unusable or rejected magic chats waits for the lists the same way, since the owner's usable chat may be on a later page, and raises `magic_ineligible` only once they are complete. With complete lists and no magic chat it creates a megagroup, which it then archives and mutes; a bound chat still missing from complete lists is gone (`chat_gone`). The chat a lookup created counts as found for the rest of that lookup, since the lists may show it only later.

Core sorts each failed request (`ClassifySyncChatError`). Only `FLOOD_WAIT_n`, `FLOOD_PREMIUM_WAIT_n` and `SLOWMODE_WAIT_n` are waits: one of up to 30 seconds is retried once in place, and a longer one is kept in sync/chat.json under its method, so it holds across restarts and for every trigger. Only such a kept flood is a Telegram wait. A timeout, network failure, 5xx or 401 is transient: the lookup backs off 5, 10, 20, 40 and then 60 seconds in memory only, and a restart does not inherit it. Anything else is a refusal and raises its problem (`SyncChatRefusalProblem`): `create_limit` for creation limits, `chat_gone` for a private or invalid channel's full info, otherwise `request_refused`. A refused full-info read of a candidate that is not the bound chat only rejects that candidate. A lost reply to `channels.createChannel` blocks another creation for a day. Archive and mute failures are only logged. A problem of the bound chat (it is gone or left, has another member or admin, or cannot be used) is recorded once, answered without requests by every trigger and cleared only by a manual check, which then decides afresh. Another candidate that fails verification (an older magic chat someone joined, say) is only rejected: core keeps it in the binding and skips it, so sync goes on in the bound chat and an unbound lookup tries the next candidate; `magic_ineligible` is raised only when none is left, and a manual check considers rejected chats again. The timed wake-up after a wait runs as trigger `retry`, never as the user's check. Record reads, posts, edits and deletions in the bound chat keep their flood waits in sync/chat.json too (see [rpc-retry.md](rpc-retry.md#waits-across-restarts)). Each step writes a `sync_chat` diagnostic line without ids or names. No sync path searches Telegram: there are no search builders, launch Saved Messages offer or discovery transport.

Sync follows the bound chat. The store that manual and automatic sync open (`PurpleAccountSyncStore.following`) belongs to the chat its state names, and when the lookup has bound another chat it moves the state there as it opens. It takes that chat from the state after recovering an interrupted atomic write, so a crash during the move (a moved `state.json.new` beside the old state, or the old state in `state.json.bak` beside the moved one) recovers the old state and the move runs again, instead of refusing the account. The move writes the automatic record first (core `MoveSyncAutoRecord`: the step in flight is dropped and the settings file on disk counts as saved), then the state (core `MoveSyncStateToChat`), and last deletes a config stage that was still pending in Saved Messages, which is abandoned because Saved Messages is no longer read. Opening removes such a stage if an interrupted move left it behind. The next automatic run finds its own head missing from the new chat and publishes the local settings there with the old base as parent; a newer version from another device in the same space is applied as usual. When the state differs from the space core selects from the chat, that is first use (below). After applying another device's head, a moved device publishes nothing while that head is still its base. A later local Save still publishes its changed bytes. Automatic sync reads, posts, edits and retires through a client for the bound supergroup built from the local chat the lookup verified, so it costs no extra request. The Sync screen runs through `PurpleSyncMagicManual`, which reads and posts in the same bound chat. Send after Save posts to the bound chat too; the explicit Send to Saved Messages action still goes to Saved Messages. A refused move leaves the state where it was, and automatic sync then holds instead of using the old chat. Each move writes one `sync_chat migration` line.

The Sync chat screen (`PurpleSyncChatActivity`, with the pure frame and pick policy in `PurpleSyncMagicScreen`) shows which chat this device syncs through, a wait with its end, or the problem that paused automatic sync. Only a flood Telegram asked for is worded as Telegram's wait; Purple's own waits (a transient failure, an uncertain creation) say when sync looks again, and while the lists load the screen keeps saying it is looking for the sync chat. A problem not shown before gets one dialog and is then marked shown in the binding, so it is not shown again until it changes. Check now runs a manual lookup, which clears a recorded problem and decides afresh. Open sync chat opens the bound supergroup. Show sync chat in chat list sets `listed` in the binding; without it Purple's chat lists hide the magic chat (`PurpleSyncChat.hiddenChat`), never a chat the user picked. The hiding is one more test in `PurpleGate.hiddenEverywhere`, which every rebuild of the main list, the archive, folder tabs and Work Mode views asks per dialog, and it answers for any non-channel dialog before reading anything; when the hidden chat changes (created, bound, shown or picked) the lists are rebuilt at once. Search and links still open the chat. Use another chat opens the local dialog list, with no search, and accepts only Saved Messages or a supergroup the user is in alone, judged from the cached member count (owner decision Q2); the lookup then checks it like any manual binding. Use Magic Purple Sync forgets the pick and keeps the waits and the list choice. For `space_mismatch` the screen offers Join: the store sets this device's own state aside (pending stage, automatic record, retained bases and last the state move into a new `orphaned-<date>` folder; nothing is deleted), the problem is cleared, and the Sync screen opens, whose next check offers to join the records already in the chat. The old setup, consent, change, Follow/Fill and stale-mark rows are gone from the screen; their classes stay until the deletion step.

First use (R4b, `PurpleSyncFirstUse`): a device with no state in the bound magic chat's space, or one whose state is in another space (review reason `space_mismatch`), reads the chat's inventory and asks purple-core (`SyncFirstUseInputOf`, `PlanSyncFirstUse`, bridged as `PurpleSyncCore.firstUse`). Wait sends nothing and says it waits for a device with your settings. Publish posts the first record with no confirmation. Join applies the chat's head with History. JoinSilently joins and keeps the file, and publishes it as the successor when its bytes differ from the head's. Ask shows the one-time choice: Use the synced settings, or Use this device's settings, which is then fed back as `SyncFirstUseChoice`. Each action goes through the runner's existing Check, apply and publish. When This device exactly matches one of several conflicting heads, the local choice first adopts that head and the runner publishes the ticket from its completion. Both conflicting heads become parents, the local file stays intact, and the next Check is settled. A state of another space is set aside (`PurpleSyncRunner.setAside`, an `orphaned-<date>` folder; settings, History and the chat binding stay) only when first use acts. Once a state exists in the chat's space the review is bound and first use no longer applies, so the question cannot come back. Automatic sync runs first use on its own (`PurpleSyncAuto`, see sync-auto.md); the Sync screen runs it after every Check. Two customised fresh devices that race into an empty chat leave one head: the second device's stale publish does not go out, and its next Check asks.

Every Check that refuses has a reason code and its own line (`PurpleSyncCheckReason`): a NeedsReview review carries core's code (`SyncConfigReviewReasonCode`: `space_mismatch`, `unreadable`, `ambiguous`, `newer_schema`, `heads_unclear`, `own_records`), any other refusal is named after its status, and the diag line is `sync check_refused reason=<code>`. First use logs `sync first_use action=<action> outcome=<result> reason=<code> archived=<0|1>`.

Automatic sync on the magic group (R4b). Every automatic pass on the magic group threw `AutomaticNonSelfHeld`: `PurpleSyncAutoCore.Inventory` still required a Saved Messages inventory, the rule of automatic sync before the magic chat, and the plan bridge copied the facts' chat into the inventory instead of being told the inventory's own. When automatic sync moved to the bound chat its facts, network and post authority changed but this guard did not. The guard now requires the inventory to be the stored state's chat (`AutomaticChatMismatch` otherwise), and the inventory carries its chat to core (`sync_auto_bridge.h`), which compares it with the state's again. An exception of any automatic pass now reaches `PurpleSyncAutoEngine.Port.failed`: the diag line `sync auto_failed reason=<code>`, a pause (core holds it as a chat problem) with an attention line, one dialog on the Sync screen, and resume after a finished Check or turning automatic sync on.

The guard of an automatic send (`PurpleSyncAutoEngine.permitted`) opens the store to compare the stored plan, and the store refuses the main thread (`PurpleAccountFileSnapshot.worker`). The chat lookup's gate (`PurpleSyncChat.underLock`) asks that guard on the main thread, so every pass planned its post or edit and then refused it locally with `send_not_postable`, without a lookup. On the main thread the guard now checks only that automatic sync is live; the worker runs the full check before each send and again in the last check before the post. The host device (`PurpleSyncMagicDevices.Automatic`) asks the guard on a thread the Looper stub calls main.

A failure on the automatic path is transient unless it can only be fixed by hand (R4b, `PurpleSyncAutoEngine.failure`). Only `automatic_chat_mismatch` and `native_unavailable` pause automatic sync (`pausing`); any other failure logs `auto_failed` with its reason, shows the retry time and retries with the usual backoff. A device whose file already means what the chat's newest head means settles with no prompt: core holds that verdict (Adopt) as NeedsReview, so the engine reviews the read inventory, commits the head as its base through the same apply path as a manual Check, writes no settings and plans again (`adoptSameHead`). A tapped first-use answer is stored before the Check that acts on it (`PurpleSyncFirstUse.remember`), so a crash between the two does not ask again. An Ask or Wait result is stored under `PurpleSyncFirstUse.shownKey`, so the status line stays true after a restart, while `held()` reads only the live result, so a stored answer never stops a device from checking again. The attention line opens the sync screen, which runs one Check on open so the choice is on screen.

Known limits (R4b). Two installs that shared a Saved Messages space land in one space with no first use in every order the host cases cover (`migrationBothPublished`), but if D never read A's newer R2 and D moves first, D's older settings reach the group as a new version R2 does not descend from: A holds on Conflict with its file intact and a Check offers the choice. Two fresh installs that race on an empty chat can each publish their own space. `PurpleSyncChat.spaceMismatch` compares the device's space with core's selected space even when the inventory also holds that device's records. The other device enters first use at its next complete Check: equal settings join silently, and different settings ask for the one-time choice. Both paths preserve the local file until an answer acts.

Moving to magic keeps the space. The device run of R3/R4 ended Android in AccountUnbound and a fresh space although the devices shared a space before magic. Automatic sync passed the moved state to core as no state whenever the account recovery scan (`PurpleSyncRecoveryModel`, built for Saved Messages) did not answer Bound, and in a magic chat that scan refused the sync folder for entries unrelated to the binding: on those builds `chat.json` behind the `/data/user/0` link, and still leftovers of older builds such as `sync-chat-setup.json` or carry files. So automatic sync held AccountUnbound and never published the moved state into the magic chat; what the chat then received came from a first publish without a state, which starts a new space. Automatic sync now uses the scan only for Saved Messages (`PurpleSyncAutoEngine.recoveryScanApplies`), as the Sync screen already did. The store's move now takes the settings fingerprint from a plain read of the file instead of the Android editor's read, which opened the editor and the gate inside a store open for bytes the move does not need. The space mismatch that remains (D1: the chat holds a fresh space, the other device the old one) is first use's one-time choice instead of a refusal.

First use keeps the user's answer per account with the chat space it answered for (main settings), until first use acted on it, so a crash or a failed step after the old state was set aside does not ask again. Automatic sync of a device with no state runs first use when turned on or after a real Save, and on the lifecycle triggers at most once per 15 minutes (`PurpleSyncFirstUse.due`).

Core lists one head per install (`ExtractSyncConfigHeads`); first use counts only the chat's current heads (purple-core 493d0db, `MaximalConfigHeads`) and names the head key (`SyncFirstUseInput.headKey`, bridged as `FirstUse.headKey`). The client never derives the head: `headKey` is the chosen key of Join and "Use the synced settings", and the one expected parent when JoinSilently with other bytes or "Use this device's settings" publishes this file as the successor on a fresh check. JoinSilently with the head's exact bytes joins with the local choice, because the review lists that head as the same and `PlanSyncConfigApply` refuses its key (InvalidChoice). The host case R1 (install D) and R2 (install A, parent R1) covers Join, both silent joins and "Use the synced settings".

Purple builds from before Magic Purple Sync keep reading and posting in Saved Messages, so a device that is not updated drifts apart from the updated ones until it is (owner decision Q5).

The broadcast policy is CreatorAndSoleAdmin. Broad outgoing-only acceptance stays disabled. Saved Messages does not need `out=true` or a sender, but excludes forwarded, bot, scheduled, TTL and nonregular messages. Private ownership uses `out`; groups also need the self sender. Android substitutes the dialog peer when `from_id` is absent. The mapper preserves the original sender flag: an absent group/supergroup sender stays Unknown, explicit other senders stay Other, and outgoing private behavior is unchanged. Channel admin counts require affirmative full-info flags. Basic groups use a unique full roster containing self; forbidden rosters remain unknown. Active secondary channel usernames count as public.

## Record transport and account authority

The modern native record client applies shared C0 ownership to both scan candidates and fresh metadata. Unknown scan ownership makes the scan incomplete. Fresh Unknown/Other is a failed/changed read, never Empty. Known excluded scan rows retain their ids so pagination still advances. The owned history response normalizer rejects inexact/flood, unexpected constructors, wrong-route messages and contradictory counts. The wrapper retains a declared total across constructors, requires it to stay stable whenever supplied, requires full declared coverage before accepting any empty tail, and fences obsolete scan replies. Reaching history page 1,000 is Unknown, even if that page is terminal; terminal page 999 can complete. Only exact complete history plus validated candidate reads can produce Empty/Present. Native inventory now captures fresh full info and reads the exact typed chat, including channel-scoped exact reads. No read route substitutes Self for a missing peer or access hash.

`PurpleSyncChat` is the active account facade for Magic lookup, status and before-post admission. The caller captures an origin and account lease, then rechecks the exact typed route and account/login before effects. `PurpleSyncReader.RecordReceipt` seals validated transport metadata; `PurpleSyncRecordSnapshot` captures the strict TL snapshot and `PurpleSyncRecordCore` validates the receipt/hash through `sync_record_bridge.cpp`. Receipt scope, hash, message bounds and ownership remain required for complete inventory.

The removed search/mark/setup/carry controllers were dormant. Their still-active durable-file and retained-base JNI implementations live unchanged in `sync_files_bridge.cpp`. Account locks, ordinary upload authority, first-use History and archive integration remain active. Opaque artifacts from older builds are still refused or set aside under the existing first-use rules. Cleanup does not delete user files. Old localization keys stay allocated to preserve compatibility with cached language packs.

## Host checks

The canonical host roster retains ownership/eligibility, typed scanner/reader, exact metadata, upload/post-effect, account-lock and Magic/automatic/first-use cases. The record bridge has exact-byte and invalid-envelope cases. The ordinary upload still requires its current account capability at every post and exact owned readback before confirmation. See [automatic sync](sync-auto.md) and [RPC retries](rpc-retry.md). Host qualification uses synthetic ports, with no GUI, device or Telegram requests.
