# Sync-chat discovery

Purple normalizes Android TL objects into the shared sync-chat contract. `PurpleSyncChatCore` supplies typed ownership, eligibility, exact mark parsing, cache ordering and resolution through `sync_chat_bridge.cpp`. `PurpleSyncChatFacts` maps current native message, peer and matching full-info objects; missing or unrecognized facts stay Unknown. Eligibility needs current matching full info, explicit file-send rights and the current send-as choice. Origin includes account slot, environment, user and a per-login token. The token stays local.

The broadcast policy is CreatorAndSoleAdmin. Broad outgoing-only acceptance is unavailable. Saved Messages does not require `out=true` or a sender, but still rejects forwarded, bot, scheduled, TTL and nonregular messages. Private ownership uses `out`; group ownership also needs the self sender. Android's deserializer substitutes the dialog peer when `from_id` is absent. The mapper preserves the original sender flag: a missing group/supergroup sender remains Unknown, explicit other senders remain Other, and Saved Messages/private behavior is unchanged. Channel counts are usable only when their full-info flags are present. Basic-group population uses a unique full roster containing self; forbidden or missing rosters remain unknown. An active secondary channel username is public too.

Core performs mark grammar checks, sorting, deduplication, tie-breaking and resolution. Unknown direct reads preserve the effective read cache while holding posting. Follow, Fill and ReadWinnerInventory return a held plan; this bridge never changes settings state or commits a moved cache. Searching delays are 30, 120 and 600 seconds. Automatic non-self sync remains disabled by the existing core guard.

## Source and host JNI checks

`TMessagesProj/jni/purple_jni/tests/run_sync_chat.py` compiles only the Purple mapper/bridge model and host fixtures against an existing qualified Java classpath. Supply `--receipt`, `--json`, `--library` and `--output`, first with `--phase compile` under the shared compiler hold, then `--phase run` after releasing it. The host library must contain the current JNI bridge and pinned core. The fixture uses genuine `TLRPC` classes and serialization; its only Android process shim reports the test environment. Class-origin assertions prevent replacing the production mapper or TL objects with fixture copies.

These are deterministic source/host cases, not native Android or Telegram qualification. R1/R2 self parity, multi-page server behavior, other-author broadcast acceptance and migration remain subject to their native gates. R2 stays enabled until an explicit per-client parity decision. No test here contacts Telegram or posts anything. Source completion, app compilation and native acceptance are separate gates.
